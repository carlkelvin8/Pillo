Scope: static review of the code at `f113db1` plus the automated checks below. It is not a penetration test. Nothing here was exercised against live Supabase, a live PayMongo account, or a live model.

## Data flow (as built)

- **Staff app:** browser -> Server Component or Server Action -> `supabase-js` as the signed-in user -> Postgres with RLS. `clinic_id` comes from `getWorkspace()` (membership), never from the client. Good.
- **Money:** staff create invoice (`create_invoice`) -> send -> payment link (PayMongo) or manual cash/bank -> webhook `/api/webhooks/paymongo` (HMAC on raw body) -> `apply_provider_payment()` (service role, idempotent) -> trigger marks invoice paid. Good design; gaps below.
- **Public patient surfaces:** `/chat/<slug>` and `/api/chat/*` (conversation token, only the SHA-256 stored), `/offer/<token>` (service role, scoped by token hash). Rate limits are in memory per instance.
- **MCP:** `/api/mcp` bearer token -> hashed lookup -> **direct Postgres connection via `DATABASE_URL`** (not supabase-js, so no RLS) -> hand-written SQL scoped by `clinic_id`.
- **Dr. Pill:** service-role store scoped to one clinic and one conversation; model never supplies a clinic id. Live model calls are now off unless `LIVE_AI_ENABLED=true`.

## Findings

Severity is my judgement of risk if this ran with real clinics today.

### High

1. **FIXED in `20261204000000_void_cancels_pending_links.sql` (apply it to Supabase): payments can arrive on a voided invoice.** Voiding now cancels open links, and the webhook refuses non-pending payments (`not_pending`, logged for review). The PayMongo-side link is still not archived. Original finding: `voidInvoiceAction` and the `guard_invoice` trigger only block voiding when a *succeeded* payment exists. A pending PayMongo link stays payable. The webhook then marks the payment succeeded, the money counts toward the balance, and the invoice is void. Fix: void must cancel pending links (and ideally the provider link), in one transaction.
2. **All clinics share one PayMongo account.** `getPaymentProvider()` reads one `PAYMONGO_SECRET_KEY`, so every clinic's money lands in the platform account. Needs a model decision (per-clinic keys, PayMongo marketplace/sub-merchant, or legal review) before any live payment.
3. **Staff invitations only work for brand-new users.** `accept_pending_invitations()` is called only when the user has no membership (`workspace.ts`). A person who already belongs to a clinic, or who created their own clinic first, is never added. No invitation email is sent either, so the owner has to tell people to sign up with that exact address. There is also no clinic switcher.
4. **MCP bypasses RLS.** It uses `DATABASE_URL` (likely a privileged role). Tenant isolation depends on every hand-written query containing `clinic_id`; I checked all eight tools and they do, but one missed clause becomes a cross-tenant leak. Use a dedicated least-privilege Postgres role, or route MCP writes through the same RPCs.

### Medium

5. **No security headers.** `next.config.ts` sets none: no CSP, `frame-ancestors`/`X-Frame-Options`, HSTS, `nosniff`, `Referrer-Policy` (only `/offer` sets a referrer policy). `/offer/<token>` has an accept button, so it is clickjackable.
6. **AI chat can forge patient consent (latent while live AI is off).** `findOrCreatePatient` matches on phone + `ilike(full_name)` and sets `consent_at` if missing, with no identity check. Anyone who knows a patient's name and number can "consent" for them, which unlocks Chair-Filler outreach. `ilike` also treats `%` and `_` in the name as wildcards. Needs OTP (planned 4C) or no consent updates for existing patients.
7. **MCP hardening.** Tokens never expire, there is no rate limit, and the audit entry records only the tool name, not which patient or appointment was read (weak for RA 10173 audit). Raw database error text is returned to the client. If the audit insert fails after a successful write, the call reports failure, inviting a duplicate retry.
8. **Orphan PayMongo links.** `requestPaymentAction` creates the provider link first, then inserts the payment row. If the insert fails (for example two clicks racing past `guard_payment`), the link exists at PayMongo but is unknown here, so a payment would be `unknown_reference` and the money is unrecorded.
9. **`log_audit()` lets any member write any action, entity and meta.** The audit trail can be polluted or made to look like another action, and `meta` is not checked for patient details. Restrict to an allowlist of actions or write audit rows only from server-side triggers/RPCs.
10. **Rate limiting is per instance and keyed on `x-forwarded-for`.** On serverless, counters reset per instance and the header is spoofable unless the platform overwrites it. Treat it as speed bump only; use a platform firewall or a shared store.
11. **Unknown PayMongo sources are labelled "bank"** (`mapPaymongoMethod` default), which skews the payment-method mix.
12. **Manual cash/bank payments have no second approval.** A receptionist can mark any sent invoice fully paid. It is audit-logged, but there is no reconciliation view.

### Low and notes

- Any confirmed user can call `create_clinic()` without limit.
- Chair-Filler `acceptOffer` is several non-transactional writes after the atomic claim; a mid-way failure leaves partial state. There is no patient-overlap check (a patient can be double-booked with themselves).
- `appointments.reason` is readable by every member, including billing. Keep clinical detail out of it.
- Emergency detection is a short regex list; the bare word "emergency" is a false-positive source and many real phrasings are missed. It is a safety net, not a classifier.
- The reminder switch (`send_reminders`, `send_reminder` on appointments) exists but nothing sends reminders.
- Doc drift: CLAUDE.md says the Claude API, the code uses Gemini; SPEC still lists a Withdraw modal and `request_payout`, which a migration dropped.
- Good: Zod validation on actions, composite `(clinic_id, id)` foreign keys, the no-double-booking exclusion constraint, hashed tokens, `safeNext` open-redirect guard, webhook signature on the raw body with a 5-minute window, service client confined to public routes, no `dangerouslySetInnerHTML`/`eval`, no vulnerable dependencies.

## Suggested order

1. Fix finding 1 (void cancels pending links) and add a test for it.
2. Decide the PayMongo model (finding 2) before applying for production keys.
3. Fix invitation acceptance (finding 3), or document "sign up first, then invite" for pilots.
4. Add security headers (finding 5).
5. Give MCP its own database role and expiring tokens (findings 4, 7).
6. Playwright e2e for the three critical flows (sign-up to onboarding, book appointment, invoice to paid).
7. Landing page with a pricing placeholder for the pilot, then reminders (the likeliest first Phase 6 item).
